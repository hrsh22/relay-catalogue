# Relay: source-based Loops evaluation

This review applies the freshly retrieved `loops evaluate --event road-to-devcon-v --problem steward-succession --format json` prompt to implementation [52139be](https://github.com/hrsh22/relay-catalogue/commit/52139be200c0e867ff46f7e58f7d129c86a581fd). The command was rerun after that implementation commit and returned the same rubric prompt. The [evaluation receipt](../evidence/code-evaluation.json) records its timestamp and hashes. It is a private alignment assessment, not an official Loops score. No numeric score is assigned.

## Alignment summary

Relay preserves a public catalogue identifier while a threshold council changes its publishing authority. The follow-up makes the existing portable-proposal architecture usable through a council desk, gives delegates a readable review packet, adds review and intake of contributor corrections, and strengthens validation at the signing and spending boundaries. The code enables separate keyholders; the recorded live rehearsal still used identities controlled by one builder, and does not demonstrate independent people operating across different machines.

## Verified from source

- **Separate holders can exchange public proposals.** [The council session launcher](../scripts/operator.ts) supports `--council` without starting or probing Bee. [The operator API](../src/app/api/operator/route.ts) returns an explicit public configuration and installed identity aliases, while treating storage observation separately. [The council workbench](../src/components/council-proposal.tsx) imports, reviews, approves and exports public proposal JSON. Eligibility comes from current council owners and an installed key, not an address merely listed in configuration. [Holder setup](INDEPENDENT_COUNCIL.md) describes installing only the holder's own key.
- **An unavailable outgoing feed does not gate council authority.** [The operator panel](../src/components/operator-panel.tsx) reads its authority through the separate `registry-state` action and renders council review even when `current` is null. [The parent reader](../src/components/relay-app.tsx) keeps the matching operator available without a resolved catalogue. Proposal preparation still verifies the incoming feed and agreement; the old publisher's content is not required to authorize a replacement.
- **A delegate reviews what will actually be signed.** [Council validation](../scripts/council.ts) decodes and re-encodes the transaction, checks its registry, chain, Safe nonce, current owners and allowed action, and recovers every supplied EOA signature against the Safe hash. Imported appointments must also resolve their incoming feed checkpoint and readable agreement. The [review document](../src/lib/proposal-document.ts) presents these decoded fields and captured public proposal JSON as script-free HTML. It explicitly separates unsigned human context from transaction authorization.
- **Review includes the actual proposed content.** [The incoming catalogue reader](../src/components/incoming-publication.tsx) presents the verified catalogue as searchable, paginated records with library, condition, photography, folios and notes. It renders the actual agreement retrieved for the proposed reference, labels the catalogue as not yet appointed and identifies invented demonstration records. The handoff form can retain the existing agreement or propose a committee-adopted replacement; the selected reference is part of the signed appointment.
- **The human reason is collected rather than implied.** [The handoff form](../src/components/operator-panel.tsx) collects retirement, unavailability or compromise context and an explanation. The form and packet label this as supporting context. Neither code nor prose claims that a signed transaction proves death, incapacity, historical accuracy or institutional adoption.
- **Contributors' correction files now have an intake path.** [Correction parsing and edition construction](../src/lib/corrections.ts) enforce a bounded format, exact source edition, catalogue identity, existing record and valid library. [The correction inbox](../src/components/correction-inbox.tsx) presents each changed field before explicit publication through the appointed steward. A stale request cannot silently overwrite a newer edition; importing alone changes no records.
- **Authority and storage remain distinct in the implementation.** The [registry contract](../contracts/RelayRegistry.sol) delegates appointment to the council. [Publishing](../scripts/publish.ts) uses the appointed topic and dedicated key; its exclusive publisher/topic/index reservation prevents another process in the same checkout from silently replacing an uncertain append. [Storage operations](../scripts/storage.ts) capture an exact amount and depth, check the reviewed BZZ ceiling and observed batch state, and reserve each quote before submission. Fixed amounts avoid recalculating the debit from a new price. These process records do not lock independently submitted dilution of the same batch or coordinate different machines sharing one publishing key.
- **Completion is checked against the actual transaction.** [Council execution](../scripts/council.ts) records the submitted hash and requires matching Safe and registry/owner events before reporting the approved action as confirmed. Storage and feed operations retain records when their outcome is uncertain. A later read or local-record failure is not silently treated as permission to repeat an operation.
- **Collected work survives a failed refresh.** [The council UI](../src/components/council-proposal.tsx) leaves the current public proposal available to save even when revalidation fails. [The parent reader](../src/components/relay-app.tsx) retains proposals and returned receipts across dialog closure, blocks dismissal while an operation runs, and keeps the confirmed receipt available during catalogue refresh. Server-side evidence separately records submitted and confirmed transaction hashes.
- **The collective can read the arrangement.** [The agreement](AGREEMENT.md) names human responsibilities, triggers, replacement procedure and payment responsibilities. [Agreement display](../src/components/agreement-text.tsx), [the complete recovery document](../src/lib/recovery.ts) and the proposal packet present this material without requiring the committee to interpret calldata. Public originals remain public; appointment is not described as revocation of old data or transfer of a postage batch.

## Success-criteria fit

The architecture supports the required outcome: readers retain the identifier, the council can replace the publisher without that publisher's permission, contributors can prepare and submit corrections for review, and a separate custodian can renew the existing batch. The follow-up improves the practical procedure around those mechanisms. Actual continuity still includes the named humans retaining their own keys and carrying out the payment and succession agreement; the source does not establish that real institutions have adopted or rehearsed it.
