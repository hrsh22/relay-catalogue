# Strict source evaluation: Problem 3

The [latest source-only follow-up](CODE_EVALUATION.md) records the independent council workflow, correction intake and current storage implementation. This earlier review and its CI references describe the commits explicitly identified below.

## Implemented follow-up

The two reader findings below are addressed in [the current application](../src/components/relay-app.tsx). The initial list now comes only from `resolveCatalogue`: the bundled snapshot is never fetched. A supplied registry starts its network read immediately, independently of optional deployment metadata. Default address discovery validates only the address; malformed optional receipt fields cannot prevent that read. Request generations prevent a superseded lookup from installing a different catalogue.

The selected registry and connection inputs have separate state. The agreement viewer retrieves and displays the reference from the verified registry, council approval counts come from the same observed state, and deployment handoff/storage/publisher metadata is shown only for the matching registry and catalogue identity. Generic catalogue views use their own description and demonstration flag. Recovery identifiers retain the selected registry and applied public gateway, and use a known public RPC fallback so custom provider credentials cannot enter the public handover file. The operator panel and correction publisher require both registry and catalogue identity to match the configured operator. Operation completion also checks the active registry before refreshing, so an earlier operation cannot switch a reader back to a catalogue they have left.

These are implementation changes, reviewed in source. No test suite or browser run was performed for this follow-up at the builder's request. The evaluation and controlled failure receipt below describe the earlier reviewed commit and are retained as historical evidence.

## Problem 3's qualitative criterion

**Governance is exercised, not merely named.** The public registry changes the feed readers follow, and the original publishing key is absent from the council-only appointment authorization. The nine fork checks exercise actual Safe bytecode, replay protection, stale revisions, publisher/council separation and replacement delegates. The real receipts demonstrate two successive appointments. The evidence identifies the demonstration signers as operated by Harsh Gupta; it establishes a real multi-identity protocol rehearsal, rather than claiming independent institutional keyholders.

**There is no single administrator escape method.** The contract has an immutable council and no server-mediated recovery call. The CLI accepts a portable proposal and a supplied signing/executor key file; the public reader follows on-chain authority. A funded executor supplies transaction transport, not missing approvals. The agreement describes how the contributing libraries decide and how current delegates replace a departing delegate.

**The agreement is an institutional procedure.** It assigns who corrects records, who decides succession, who checks postage, when they must act, and what everyone verifies after a handoff. It accurately distinguishes stopping readers from following an old feed from revoking the old key. The downloaded reading copy uses the actual observed threshold; [a three-approval regression test](../tests/recovery.test.ts) guards against the earlier hard-coded demonstration threshold.

**Payment and authority are described as different actions.** The renewal receipt names the paying identity and existing batch; succession receipts change the appointed publisher. The agreement explicitly says that appointment does not transfer the batch and identifies the shared storage custody. Its thirty-day reserve is a working target, while the receipt records the extension actually performed. These are specific protocol and evidence facts required by this problem, not evidence of an automatic funding mandate.

## Concrete findings at the reviewed commit

1. **A failed optional snapshot can block the first authoritative read.** In [the initial effect](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L163), the default route [awaits and parses `/catalogue-snapshot.json`](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L183) inside the same `try` as `refresh(data.registry)` at line 189. A rejected fetch, invalid JSON or schema failure jumps to the outer error handler before registry/Swarm resolution starts. The effect should isolate or independently start the optional preview, so a broken preview cannot block a valid public catalogue. A [controlled execution of the current initializer](../evidence/strict-initializer-reproduction.json) confirms the call order: valid data and an HTTP 404 invoke network resolution once; transport, JSON and schema failures invoke it zero times. This uses stubbed reads and real validation, without a public write or live fault injection.
2. **Custom-registry views mix network authority with demonstration-specific stewardship information.** The [`?registry=` branch](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L176) changes only `data.registry` and `data.stableIdentifier`. The stewardship view still describes [a two-of-three demonstration council](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L689) and links [the bundled `/agreement.txt`](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L667); the storage view still uses [the demonstration saved observation](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L873), [payer and batch](https://github.com/hrsh22/relay-catalogue/blob/056e51363f6521562e088905db7ddd89d8bac620/src/components/relay-app.tsx#L905). For a different valid registry, those details are not established by that registry's state. Display the resolved council rule and registry-linked agreement, and show demonstration storage/receipt metadata only for the matching configured registry. The default demonstrated deployment's receipts remain correctly identified.

Neither finding is exercised by the current model/recovery unit tests or the contract fork checks. The first is reproduced by controlled execution of the current initializer; the second follows from the custom-registry call path. The recorded handoff and renewal remain independently evidenced.
